Building a Tiny On‑Board Anomaly Detector for ESA Satellites

2025-11-12

anomaly detectionedge aineuromorphic hardwaresatellites

TL;DR — We’re training a lightweight anomaly detector that can run on edge neuromorphic hardware (Akida).
It learns what “normal” looks like from satellite telemetry and flags surprises via forecasting errors, which is ideal when labels are scarce and compute is tight.

We combine self‑supervised learning (contrastive + masked denoising) with an Akida‑friendly CNN/SNN backbone, so the model is both accurate and deployable.

Why we did this

Satellite operations live and die by how quickly you can react to anomalies, but ships and ground stations are not always available or reliable.

Our goal:

Detect anomalies directly on‑board with minimal memory/compute, on real neuromorphic hardware (Akida).

That means:

  • Architectures must respect Akida constraints from day one.
  • Training has to handle weak or missing labels in real telemetry.
  • Everything must scale from a small sandbox setup to full‑mission data without rewriting the whole pipeline.

The data

We’re using the ESA Anomaly Detection Benchmark (ESA‑ADB) — multivariate telemetry from real missions, designed to raise the baseline for anomaly detection.

Key properties:

  • Multivariate time series (many sensors over time) → representation learning matters.
  • Events are labeled as:
    • Anomalies
    • Nominal rare events
    • Communication gaps
  • In the official test split, communication gaps are excluded.
    → The task becomes: detect anomalies + nominal rare events.

A few practical tips:

  • A 6‑channel subset (sensors 41–46) makes a great sandbox before you scale to the full channel set.
  • ESA‑ADB has both:
    • Coarse Class labels (e.g. class_4, class_7, class_11)
    • Finer Subclass labels
      Even if your main task is binary detection, this structure is gold for:
    • Diagnostics (“which classes are we blind to?”)
    • Planning a future multi‑class head.

How the model learns (without babysitting it)

The backbone of the approach is self‑supervised pretraining. We want the model to understand “normal” behavior without labels.

We explore several flavors:

  • Contrastive learning
    Siamese encoders, where positives are pulled together and negatives pushed apart.
  • CPC (Contrastive Predictive Coding)
    Use context to predict the future in latent space — focus on patterns rather than noise.
  • Non‑contrastive methods (BYOL / SimSiam)
    Predictors + stop‑gradient to avoid collapse when negatives are scarce.

Our working recipe is a hybrid SSL step:

  • Contrastive loss on latent representations
  • Masked denoising reconstruction on corrupted inputs

Both happen in a single ssl_train_step. For the reconstruction part we use Huber loss, which is more robust to the inevitable outliers in real telemetry.

At inference time, we:

  1. Use the backbone to forecast a short horizon of future telemetry.
  2. Compute |prediction − observation| per channel.
  3. Use these residuals as the anomaly score.

If the model has learned “normal” behavior well, you don’t need labels at test time — high residuals simply mean “this doesn’t look like what I’ve seen before.”

Architecture — tuned for Akida (gotchas included)

We designed the architecture around the hardware rather than treating Akida as an afterthought.

Some constraints and lessons:

  • Asymmetric conv kernels (e.g. 7×1) are not allowed.
    Use symmetric kernels such as 3×3, 5×5, 7×7 instead. We only realized this after the first backbone upgrade failed conversion.
  • Stick to Akida‑friendly ops:
    • ReLU6
    • MaxPooling
    • GlobalAveragePooling
  • Avoid exotic layers and stick to patterns that convert cleanly to SNN primitives.

The overall structure:

  • A shallow temporal CNN backbone that focuses on:
    • Early extraction of temporal patterns
    • Minimal channel mixing up front
  • Optional 1×1 conv layers later for light channel fusion
  • A small forecasting MLP head that outputs [horizon, channels]
    → Residuals between this forecast and the true future become the anomaly score.

Design rule: Respect SNN/Akida constraints from the start — retrofitting later wastes a lot of time.

Training workflow & small fixes that saved us hours

A few practical details that turned out to matter more than expected:

  • Train mostly on normal segments (y = 0)
    → The backbone internalizes “healthy” behavior and becomes sensitive to deviations at test time.
  • Windowing matters. One configuration that worked well:
    • Input: 1‑hour window
    • Forecast: next 30 minutes
  • Losses and metrics:
    • For binary detection: compile with AUC and monitor val_auc.
    • Don’t monitor val_auroc unless you actually added it — we once had a model that never saved “best” weights because the monitored metric didn’t exist.
    • For SSL / pure regression phases: monitor val_loss and drop “accuracy” — it is meaningless there.
  • Normalization trap:
    In estimate_norm_stats_ssl, x.shape[0] can be None with dynamic batches.
    → Switch to tf.shape(x)[0] when accumulating statistics.
  • Reproducibility:
    • Keep the whole stack containerized (docker build …, docker run …).
    • Use a few SLURM one‑liners for queueing experiments and cleaning up jobs while iterating quickly.

How we judge success

We evaluate from several angles:

  • Supervised metrics (when labels are available):
    • ROC‑AUC
    • PR‑AUC
      for Anomaly vs Rare Event.
  • Unsupervised view:
    • Percentile‑based thresholds over forecasting residuals for early flagging.
  • By taxonomy:
    • Report metrics per Class/Subclass to identify blind spots:
      • e.g. strong on class_7, weak on class_9.

This class‑wise view is also a sanity check before adding a multi‑class classification head later on.

What surprised us

  1. SNN/Akida constraints are real.
    If you don’t design with the allowed ops/kernels in mind from day one, you end up rewriting the backbone.
  2. Data understanding beats model tricks.
    Relationships among channels and the time ranges you choose can make or break performance.
  3. Architecture should follow the signal.
    Time‑series structure should drive kernel sizes, stride choice, and when/how you mix channels.
  4. Most bugs weren’t “deep learning magic,” they were plumbing.
    Training loops, callbacks, normalization, and metrics caused more issues than the network definitions themselves.
    → Another reminder to own every line of the pipeline, not just the model.

What’s next

  • Finalize the Akida‑compliant backbone
    (symmetric kernels, GAP, ReLU6) and thoroughly test it on the 6‑channel sandbox before scaling up.
  • Keep iterating on the hybrid SSL recipe
    (contrastive + denoising) and enrich time‑series augmentations:
    • masking
    • noise injection
    • time shuffling
  • Clean up metrics and checkpoints across phases:
    • Consistent logging
    • Results broken down per Class/Subclass
  • Once the backbone is stable, start experimenting with:
    • A multi‑class head for anomaly type prediction
    • Deployment prototypes on real Akida boards
